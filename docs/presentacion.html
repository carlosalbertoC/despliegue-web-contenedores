Aplicación web con base de datos en contenedores

Inicio de sesión contra PostgreSQL, tres contenedores en local y publicación con HTTPS.

Integrantes: completar los nombres del grupo.

Presentamos el despliegue de un portal con usuario y contraseña. La cuenta se comprueba en PostgreSQL. En la laptop hay tres contenedores. En la nube la misma aplicación queda en una URL HTTPS.

Objetivo

Qué tiene que quedar demostrado

  • Un formulario público y una bienvenida que solo aparece con sesión válida.
  • Dos cuentas de prueba, con la contraseña guardada como hash bcrypt.
  • Proxy, aplicación y base en Compose: red interna y volumen.
  • Imagen propia portal-acceso:1.0.0 para linux/amd64.
  • La misma aplicación publicada, con la base fuera de internet.

El laboratorio anterior era una página estática en un solo Nginx. Aquí hay estado, un secreto y más de un servicio. El resultado visible es la URL: entra quien tiene la clave y no entra quien no la tiene.

Arquitectura local

Tres contenedores, dos redes

Nginx 1.27.5Única puerta. Publica el puerto 80 y reenvía a la aplicación. Red web.
Aplicación Node.jsValida el formulario, abre la sesión y pinta el saludo. Redes web y datos. Sin puerto en el host.
PostgreSQL 17.6Tabla usuarios. Solo red datos, sin puerto publicado. Volumen pgdata.

El navegador solo habla con Nginx. Nginx no está en la red de la base, así que no puede consultarla aunque alguien cambie el proxy. El volumen es lo que permite borrar el contenedor de PostgreSQL y seguir teniendo las cuentas.

Opción A

Blitz Cloud para la URL pública

  • Se publica la imagen de Docker Hub, construida para amd64, en el puerto 3000.
  • PostgreSQL 17 lo administra la plataforma e inyecta DATABASE_URL.
  • La base no tiene dirección pública. El HTTPS lo entrega Blitz.
  • Nginx no se despliega en la nube. Los tres contenedores se muestran en local.
  • El plan gratuito evita la tarjeta y los créditos que vencen en una máquina virtual.

Elegimos la opción A porque la base administrada ya viene cerrada a internet y con copia nocturna. La arquitectura completa se sostiene en Compose, que es lo que la rúbrica pide demostrar en local para esta opción. Hay que abrir la URL unos minutos antes: a los treinta minutos sin visitas la aplicación se duerme.

Despliegue

Del repositorio a la URL

  1. Completar .env, que no se sube a Git.
  2. docker compose up -d --build y probar los dos usuarios.
  3. docker build --platform linux/amd64 y docker push de la etiqueta 1.0.0.
  4. En Blitz: imagen, puerto 3000, PostgreSQL, SESSION_SECRET y COOKIE_SECURE=true.
  5. Abrir la URL HTTPS y repetir el acceso válido, el inválido y /bienvenida sin sesión.

El esquema SQL lo aplica la propia aplicación al arrancar. Hace falta porque la base de Blitz no ejecuta el entrypoint de la imagen oficial de PostgreSQL. En local ese mismo script es idempotente y el volumen conserva los datos.

Seguridad

Qué queda cerrado

  • La contraseña no se guarda en claro. El hash bcrypt empieza por $2a$12$.
  • La consulta usa el parámetro $1. El texto del formulario no se concatena.
  • La clave de la base y el secreto de sesión solo existen como variables de entorno.
  • La cookie de sesión es httpOnly. En la nube, además, Secure.
  • /bienvenida responde con redirección si no hay sesión.

En la demostración se ve el hash en psql y se intenta abrir la bienvenida en una ventana privada. Esas dos pruebas cubren el almacenamiento y el control de acceso. La red se muestra en el archivo Compose: la base no tiene ports y no está en la red del proxy.

Límites

Problemas, lecciones y mejoras

  • En Apple Silicon hay que forzar linux/amd64 antes del push.
  • El init oficial de PostgreSQL no corre si el volumen ya tiene datos, ni corre en Blitz. El arranque de la aplicación cubre los dos casos.
  • La cookie Secure no puede activarse en el HTTP local.
  • La sesión está en memoria: vale para una instancia, no para varias réplicas.
  • Después de exponer, borrar la app y la base en Blitz, y bajar Compose.

La mejora siguiente, si esto dejara de ser una entrega, sería guardar la sesión en un almacén compartido y sacar los secretos de variables sueltas hacia un gestor. No lo hicimos porque la rúbrica pide una instancia y variables de entorno, y conviene poder explicar todo lo que sí está desplegado.

Cierre

Relación con la nube

  • Portabilidad. La imagen lleva el runtime. El destino no instala Node a mano.
  • Administrado y autogestionado. En local operamos la base. En Blitz la operan y la aíslan.
  • Límites del gratuito. Memoria acotada, una base y suspensión a los 30 minutos.
  • Persistencia. El volumen sobrevive al contenedor. La capa del contenedor, no.

La imagen es el artefacto portable. La base administrada muestra el otro modelo: dejamos de operar PostgreSQL y seguimos siendo responsables de la aplicación, del esquema y de borrar el recurso al terminar.

Demostración · 5 minutos

Guion en la URL pública

  1. Abrir la URL y mostrar el formulario.
  2. Entrar con ana.garcia / Nube-Ana-2026 y mostrar el saludo a Ana García.
  3. Probar una contraseña incorrecta y mostrar el rechazo.
  4. Abrir /bienvenida en una ventana privada.
  5. Mostrar en Blitz la aplicación y la base. En local: docker compose ps, el hash y el volumen tras recrear db.

Segunda cuenta, por si hace falta: luis.torres / Nube-Luis-2026.

Seguimos ese orden y no nos adelantamos a la ventana privada: la cookie de la sesión anterior haría parecer que la página no está protegida. El hash y el volumen se muestran en la laptop, porque a la base de Blitz no se entra desde fuera.
